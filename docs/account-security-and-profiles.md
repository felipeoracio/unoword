# Account security and writing preferences

The extension uses the existing Supabase user and HTTP-only secure cookies. Account changes call GoTrue with a freshly reauthenticated user token. They never call the admin user-update API, create a replacement account, or transfer data by email. Profile, documents, memory, saved ideas and entitlements remain keyed by the permanent Supabase user ID. `/auth/me` reads the current provider identity, so verified email changes appear when the popup reopens; an email claim in an older JWT is not authoritative.

## Required Supabase email configuration

Email changes and recovery requests stay unavailable until deployment setup is complete. Password updates work through Supabase's password API. Security-notification delivery requires the provider settings below; the application does not claim delivery.

1. In Supabase Authentication → Email, configure production SMTP and a verified sender. Enable email confirmations, **Secure email change** (both current and new addresses), and the security notifications for password changes and email changes. Keep the existing signup behavior unchanged. Configure an appropriate password policy, OTP expiry, and provider email/IP rate limits. Supabase enforces those limits across Vercel instances; the application adds a bounded, per-instance burst limiter.
2. In Authentication → URL Configuration, use `https://unoword.vercel.app` as the Site URL and allow `https://unoword.vercel.app/account/security` as a redirect. Add explicit preview hosts only if needed; set `PUBLIC_APP_URL` and `AUTH_ALLOWED_ORIGINS` accordingly in that deployment. Never derive a redirect from an untrusted request header.
3. In the **Reset password** email template, replace the action link with:

   ```html
   <a href="{{ .SiteURL }}/account/security?token_hash={{ .TokenHash }}&amp;type=recovery">Reset password</a>
   ```

4. In the **Change email address** email template, use:

   ```html
   <a href="{{ .SiteURL }}/account/security?token_hash={{ .TokenHash }}&amp;type=email_change">Verify email change</a>
   ```

   Supabase's secure email-change workflow sends the confirmations to the original and new addresses. Preserve the provider's email-change notification to the original address. Each address must be verified before the account email changes. Use this template for the confirmations generated by that workflow; do not substitute an admin-generated link in production.
5. Check delivery to controlled old/new inboxes, including spam folders, and the provider email logs. Then set **`AUTH_SECURITY_EMAILS_CONFIGURED=true`** in Vercel for the intended deployment environments and redeploy. This flag represents the administrator's completed SMTP, template, notification, and secure-change configuration. Do not enable it merely to dismiss the setup message.
6. Reload the unpacked extension (v0.13.0) or install the updated package. Open Settings → Account & Security. Verify a real change with inboxes you control. Keep both emails until confirmation completes.

The callback page requires the one-use `TokenHash` templates above. It clears the link query immediately and submits the token in a POST body after user interaction. Recovery verifies and consumes the token only when the new password is submitted. The default implicit-access-token fragment link format is intentionally rejected with a setup message. No access or refresh tokens are returned to the extension or stored in local storage. The callback has no analytics and uses `Referrer-Policy: no-referrer` via the page's referrer metadata. A reloaded, already consumed or expired recovery link requires a new email. If the provider rejects a new password after token consumption, request another link.

Password change requires current password, matching new passwords and Supabase policy approval. It creates a freshly reauthenticated current session, changes the password on that same user, and revokes other **refresh sessions** with GoTrue `logout?scope=others`. The UI reports a revocation failure separately. Already issued access JWTs can remain valid until their configured expiry; configure a suitable Supabase access-token lifetime. Password fields clear after submission, cancellation, navigation and account changes. Request validation responses omit submitted values. Social-only identities receive guidance to manage credentials through their provider; [Google sign-in](google-oauth.md) reuses these accounts and sessions without automatically adding a password identity.

## Plans and profiles

The existing [Stripe integration](stripe-billing.md) keeps signed-out plan actions pending until sign-in and requires account-specific confirmation. `/subscription/change` checks auth, browser origin, confirmation and expected account ID. Billing stays unavailable when deployment settings are incomplete, and only verified payment-provider events can change Stripe-backed entitlements. Checkout or Google sign-in redirects alone never grant access. Live billing requires separate owner approval.

Library → **My Writing Profile** clones the eight existing onboarding questions. Both screens use `/ai/profile` and the existing `ai_profiles` row. Selected themes live in `ai_preferences.prompt_themes`; no migration or second preference table is needed. Free users can edit profile answers; custom theme editing remains a Pro feature. Local profile data is only an owner-scoped cache. Explicit saves replace all eight fields, including empty values, preserve unrelated preferences, and mark the profile as edited. Older `ai_onboarding_answers` provide missing values until the first explicit profile edit; after that, outdated answers cannot restore cleared preferences.

Every AI request loads the authenticated user's latest profile and themes, then builds bounded context with those explicit preferences first. Current preferences override conflicting inferred interests. An expansion retains its current draft as the main focus, and connections still require two distinct real sources. Older suggestions grounded in a pre-edit profile are excluded from the automatic context. Existing source-availability filters still exclude deleted/disabled source text and derived memories. Attribution uses only source IDs actually sent to the model; an empty citation list has no claimed source explanation. Free and Pro Original suggestions retain the local library and incur no AI usage.

## Validation

Run selected unit suites (avoid unrelated live tests that alter shared production settings):

```sh
python -m pytest backend/tests/test_account_security.py backend/tests/test_profile_personalization.py backend/tests/test_suggestion_modes.py backend/tests/test_suggestion_breadth.py backend/tests/test_phase15_cost.py
node --test extension/tests/*.test.js
node extension/tests/profile-security.browser.cjs
node extension/tests/dashboard.browser.cjs
node extension/tests/suggestion-modes.browser.cjs
# After building frontend:
node frontend/tests/account-security.browser.cjs
```

The browser suites use actual popup and service-worker code with isolated Chrome/HTTP fixtures. They cover EN/ES, 180–420px, profile saves/clears/Cancel/error retention, cross-account caches, pending email, visibility toggles and credential cleanup, plan sign-in/confirmation, and all four suggestion options. Native unpacked-extension execution can be restricted by browser administration policy; these fixtures do not bypass that policy.

Live checks during implementation created and deleted isolated Supabase QA users. Actual password changes invalidated the old password, preserved the current session and Pro/profile data, and revoked other refresh sessions. Provider-generated recovery links completed successfully and failed on reuse. Provider-issued email confirmations verified both addresses before changing the email on the same ID; invalid/reused links failed. Those checks bypassed mailbox delivery using GoTrue's test-link generation. They do **not** certify SMTP delivery, notifications, or installed-extension cookie behavior. Complete the controlled-inbox test above before enabling email changes and recovery in production.

Implementation verification: 90 selected backend tests, all extension unit suites, three popup browser suites, the built callback browser suite, and the frontend production build passed. The older shared-account `test_knowledge_pipeline.py` suite was not run against production: its local-server fixture was unavailable and it resets shared QA usage. Isolated live accounts were used for the credential checks instead. The build retains its existing bundle-size advisory; no build errors occurred.
